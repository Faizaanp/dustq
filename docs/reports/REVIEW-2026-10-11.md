# Review — implementation and docs after T0/T1 (2026-10-11)

Scope: every file in `dustq/`, `scripts/`, `tests/`, `configs/`, and `docs/` (planning, reports, HYPOTHESES, OPEN_QUESTIONS, PUBLICATION_STAGES, REPO_MAP, paper_tables, related_work), checked against the pinned upstream (`b20f7c0`) and Plan v3.1.

Method: code read plus a CPU probe script that reproduces each bug. The script is kept outside the repo, in the agent's scratch folder (`scratch/review_probe.py`). All results below were reproduced with the project `.venv`, except the GPU-only item (B4), which is from code inspection.

**Verdict:** the docs are high quality, and the core estimator work (DUSTQ bitwise-equal to DUST, recipes, exact resume) is solid. But **the first Colab session would fail as the code stands**. Five blocking bugs (B1–B5) must be fixed before any L4 time is spent. None of them is caught by the current tests, because every test runs on CPU at the `tiny` size.

## Blocking (fix before the Colab session)

## Correctness issues (fix before T5 / any quantized results)

| ID | Issue | Evidence | Fix |
| --- | --- | --- | --- |
| C1 | Activation quantizer math runs in the input dtype. Under autocast, the attention output (SDPA) and the ReLU² output are bf16, so `x/scale` and `round` happen in bf16 | Probe: **10.5% of A8 codes differ** between bf16 and fp32 quantizer math | Violates Plan 4.2 ("fp32 math"); makes the quantizer effectively noisy, and the effect differs by site | `ste_act_quantize`: compute on `x.float()`, return in fp32 or the original dtype. The integer-code matmul (T5) fully removes grid distortion |
| C2 | Truncated runs change the data order. `_load_data` loads `cfg.steps*8` rows and shuffles that subset, whereas upstream keeps the full-budget subset when `--steps` is used | Code: `train.py:109` | Plan 6.5's short and truncated tuning runs (and any `--steps` smoke) would see different batches from the full run; batch k no longer matches | Load `budget_steps*8` rows (the upstream default for `tokens`), then run `cfg.steps` |
| C3 | Resume can corrupt `best.pt`. `best.pt` is written whenever val improves, but `ckpt.pt` only every 10 min. After a crash, the resumed `best` value can be older than the `best.pt` on disk, so a later, *worse* improvement overwrites a better `best.pt`, and `best_val` no longer matches the saved model | Code: `train.py:177-184` | Test-at-best-val can be reported on the wrong checkpoint after a Colab disconnect | Save `ckpt.pt` whenever `best` improves (cheap at these sizes), or store best weights + best value inside `ckpt.pt` |
| C4 | Activation STE passes gradient 1 **through clamp** (no clip mask) | `quant.py:26`; the test asserts grad == 1 everywhere | Harmless with absmax (nothing is clipped), but with the planned MSE-clipped A4/A2 scales it becomes a design choice that BP-STE results depend on | Decide in T5 (standard choice: zero the gradient outside the clip range, as in PACT/LSQ) and record it in HYPOTHESES / Method |
| C5 | A4/A2 still use per-token absmax (deferred in T0) | `qmodel.parse_precision` hard-codes `absmax` | A2 absmax is degenerate (most ReLU² entries round to 0). Probes or Tier B on A4/A2 before T5 lands would be invalid | Keep as is, but add a guard: refuse `w1.58a4`/`a2` with `absmax` outside smoke/test mode |

## Minor

- **M1** `queue.py`: a deterministic failure is retried on every session and appends a new `failed` row each time. The aggregator must take the last row per `run_id`; consider a max-retries marker file.
- **M2** `metrics.jsonl` gets duplicate step lines after a resume (rows written after the last ckpt are re-run). Truncate to `start` on resume.
- **M3** `benchmark.concurrent_test` uses threads in one process, which share the default CUDA stream. That does not measure "2 jobs on one L4". Use two subprocesses.
- **M4** `colab_t1.py` prints `time.monotonic()/60` as "session wall" (that is machine uptime). The sanity step runs only the recipe/sigma tests and never touches CUDA. Make it run one tiny CUDA step per precision; that would have caught B4.
- **M5** `REPO_MAP.md:93` labels the L4/d256 targets "Appendix C"; they are from **main-post Figure 4** (`paper_tables.md` has this right).
- **M6** `HYPOTHESES.md`: "With D2, n = 5 seeds; otherwise n = 3". D2 is now approved, so make n = 5 for the primary cell **unconditional**. Leaving it conditional allows optional stopping on the confirmatory endpoint.
- **M7** `T1.md` says the Tier R configs "will be picked up on the L4 unchanged". That is false until B1 is fixed (S configs crash).

## What is good (keep)

- `DUSTQ` is an exact copy of upstream `step()` with σ substitution only, and `test_dustq_bitwise_equals_dust` enforces it. This is the most important contract and it holds.
- Hook ordering (noise before quantize) is implemented correctly in both `runner.run_dust` and `train.Runner._build`, with the reason documented.
- Exact resume (generator state + optimizer momentum + data cursor) is tested bitwise for Dust and BP-STE.
- Docs: `paper_tables.md` is careful (copied verbatim, printed vs derived labelled, missing values marked). `related_work.md` has 31 verified references with the FOGZO risk flagged. The G0 targets are now concrete. The Figure-4 protocol caveat (OPEN_QUESTIONS 21) is a sharp catch. PUBLICATION_STAGES is a useful owner-facing map.
- Deviations are recorded honestly in the T0/T1 reports (the `torch.round` zero-gradient STE bug was caught and fixed by tests).

1. B1–B5 (about 1 hour), plus tests: a forward test per size, a CUDA-if-available forward per precision, and an lr-override test.
2. C1–C3 (about 1 hour).
3. Re-run the benchmark locally at `--scale tiny` for **fp and w1.58a4** to prove the script works end to end, then do the Colab T1 session.
